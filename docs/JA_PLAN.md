## 三、🔴 不能照搬前六门的（照搬会怎么错）

> 这一节是本文最重要的部分。每条都是「闸会绿、东西是错的」那一类。

**① `POS_LABELS` 的 `character: '字母'` —— 已经在表里、已经是错的、闸不会报。**
日语 `character` 是**汉字**（`犬` `馬` `国`，14,970 条），印出来是「字母·犬」。
而 `posLabel()` **没有 lang 参数**（`apps/web/src/App.tsx:647`），改共享表会把 en 的 `h`
（英语字母表第八个字母）一起改错。⇒ **必须先加 per-lang 覆盖层，这是结构改动不是补一行。**
同理 `particle: '小品词'` 对日语的助词也是错的。

**② 「含汉字 ⇒ 是中文」这条判据，仓库里 82 处，在日语上恒真。**
最要命的是翻译质量控制组（`de/pipeline/translate_defs.py:162`、pt 同款）：
```python
if not has_han(z):                              # 日语原文本来就全是汉字 → 恒绿
if len(LATIN.findall(z)) >= 2 and has_han(z):   # 日语残留是假名不是拉丁字母 → 抓不到
```
模型把 `日本語` 原样抄回来，两条都不响。**闸看着在问对错，其实在问一个恒真命题。**
⇒ 判据换成**假名残留检测**（译文里出现平/片假名 ⇒ 没翻完），比拉丁词那条更干净
——中文专名不会写成假名。
✅ 已修一处：`scripts/contract/tag_coverage_all.ts` 的 `alreadyChinese()`（2026-09-15）。

**③ `split_colloc` 在日语上 100% 静默出错。**
`de/pipeline/build_v3_schema.py:328` 靠「第一个汉字之前的最后一个空格」切分，
日语没有词间空格 ⇒ `rfind(" ")` 返回 -1 ⇒ **整条日语原文被当成中文译文**，
源语言那半是 `None`，全库命中且不报错。`pt`/`fr` 同名函数同病。

**④ `pos="character"` 在两份 dump 里是两种东西，不能按 pos 合并。**
- 英文版：漢字單字（`犬` `国`）14,970 条
- 日语版：**和語の漢字表記**（`今日`→きょう，多字词，`tags:["form-of","wago-kanji"]`）15,514 条
- **交集只有 28 个词形。** 任何「按 pos 合并两版」的脚本会把 1.5 万条异表记指针
  当成汉字条目，反之亦然。

**⑤ `inflection` 的入口判据「`forms[]` 里有 tags 的就是变形」会多收 15 万行。**
ja 的 592,334 条 `forms` 里：罗马字/canonical 218,697 + 模板残渣 16,206 要先扔；
剩 357,395 再分成 **形态 202,740 / 罗马字重复 89,513 / 正字法变体 64,900**。
名词那 39,998 行 forms **一条形态都不是**（全是旧字体/历史假名写法）。
照搬会把 20 万的真活用虚报成 35.7 万。

**⑥ PLAYBOOK 第六章「语言版 dump 收割录音」那一步，日语直接跳过。**
`[[cross-edition-harvest]]` 记的是「语言版比英文版多 436 倍」。日语实测：
英文版 6 个词形、日语版 84 个、中文版 144 个，**三版并集 206**。不是 436 倍，是三家都没有。
⇒ 别给它排工，要发音只能走 Commons 直查。

**⑦ 别把英文版当日语动词活用的源。**
它只给 975/13,921 个动词（7.0%）活用表，中位数 2 个形。照「英文版是结构基准」的惯性走，
会得出「日语动词几乎不活用」这个荒谬结论。⇒ `[[multi-edition-methodology]]`：
**英文版是结构基准，不是内容上限。**
