# 表结构重构：从「一词一行」到「一义项一行」

> 2026-08-06 设计，2026-08-07 定 v2 并落地。
> 与 `FRAMEWORK.md`（做什么、凭什么）、`PITFALLS.md`（怎么栽的）并列：本文回答**数据放在哪**。

---

## 一、为什么现在动

### 1.1 ⚠️ 多目标语言**不是**倒逼因素

本文早先版本把「目标语言扩到越南语、印尼语」写成了驱动力。用户 2026-08-07 纠正：

> 我只是说未来**可能**增加越南语等，但并不意味着现在就把位置给他留着。
> 我的想法是**可插拔式的**，想增加的时候直接加就行，而不是需要更改已有数据。

按这个标准复查，现有结构**本来就是可插拔的**：`ALTER TABLE dict ADD COLUMN
translation_vi` 是纯加法，不动任何已有数据。真正加不上去的只有 `collocation`
那一列（西语短语与中文粘在同一个字符串里，靠「从第一个汉字处切开」的正则分离 ——
越南语用拉丁字母，找不到「第一个汉字」，见 §7.1）。

⇒ 重构的真实理由是下面 §1.2 / §1.3 那两条（行号契约已咬过三次、音标正在丢变体），
   以及 §2.0.1（最贵的那份产出存成了行号）。**它们是工程质量，不是路障。**

### 1.2 按行号对齐的字符串数组已经咬过三次

`dict` 的 `definition` / `translation` / `meta` 三列是换行分隔的数组，**靠行号一一对应**。
这个隐式契约出过三次事，全是同一类：

| 时间 | 事故 | 根因 |
|---|---|---|
| 2026-08-04 | `novia` 中英错位 | `filter(Boolean)` 丢掉占位空行，后面所有行上移 |
| 2026-08-06 | `esquela` 译文错位 | 义项拆分后重新编号，旧的 idx 映射把 `[2]` 的译文装进 `[1]` |
| 长期 | 释义与指针混在一列 | `amiga` 的 translation 是 `["女的朋友", "amigo 的 阴性", …]`，展示层靠正则 `^.+ 的 \S+$` 分辨 |

一义项一行之后，**这三类错误在结构上不可能发生**：每条义项自带主键，
中文/英文/语法标记长在同一行上，没有"第 i 行"这个脆弱契约。

### 1.3 音标正在丢变体（✅ 2026-08-07 已解决）

`dict.phonetic` 一个词只存一条，源头给的远不止一条。但**「变体」有三种，性质完全不同**，
先前混为一谈导致规模被虚报：

| | 例 | 判据 | 规模 |
|---|---|---|---|
| ① 记法差 | `/ˈɡɾatis/` 与 `[ˈɡɾa.t̪is]` | **定界符**（源头明写，不必猜附标） | 音位式 22.5 万 : 严式 22.1 万 |
| ② 地区差 | `abˈduθe` 与 `abˈduse` | 有无 θ，且**成对出现**才算 | 含 θ 词头 29,134 |
| ③ 真·多读音 | `pie` /ˈpje/(脚) /piˈe/(字母读法)、`y` 五种 | ①② 归一后仍不同 | **9,813 词（5.9%）** |

⚠️ 本文原记「23.7%（33,527 词）有 ≥2 个不同音位式读音」——**那个数把 ①② 也算进去了**。
   只按 ① 算更离谱：98.8% 的词都「有多变体」。量之前先分清量的是什么。

🔴 **顺带证伪：`phoneticLatam` 的规则派生是错的。** 展示层至今用 `θ→s` 从半岛音派生，
   而源头本来就直接给了 seseo 形。实测含 θ 的 29,134 个词头：

       源头给了且与规则派生一致   28,488
       🔴 源头给了但**不一致**       630
       源头只给半岛形，只能派生       16

   那 630 条错得有规律（`sc` 在拉美是单个 /s/、词尾 `-d` 半岛读 /θ/ 拉美读 /d/）：

       irascible  半岛 iɾasˈθible  规则 iɾasˈsible ❌  源头 iɾaˈsible ✅
       Madrid     半岛 maˈdɾiθ     规则 maˈdɾis   ❌  源头 maˈdɾid  ✅
       quetzal    半岛 ketˈθal     规则 ketˈsal   ❌  源头 keˈtsal  ✅

   ⇒ 「有权威源却在自己推导」的又一实例。已改为**有源头用源头**（展示层已切）。

✅ `pronunciation` 表 **382,674 条 / 140,042 个词**（`pipeline/build_pronunciation_layer.py`）。
   `notation` 记法、`region` 地区、`is_primary` 默认展示 —— **存不存与展不展示成为两个独立开关**。
   ⚠️ 它只覆盖 kaikki 有音标的 14 万词；其余 100 万变形词仍走 `dict.phonetic`（G2P 生成），
      展示层按「有 pronunciation 行就用，没有就回落」处理，无回归。

## 二、目标结构（十二张表 · v2，2026-08-07）

> **v1 → v2 改了什么、为什么改**：v1 只有一层 `sense`，把「某一版对这个词说的一句话」
> 直接当成「用户读到的义项」。真数据装进去之后立刻穿帮：`ojo` 出 29 条并列义项，
> 其中 `[0] eye` 和 `[4] 对光敏感、使生物具有视觉的器官` 明明是同一个意思的两个面
> （对应词 / 定义），不是两条义项。
> ⇒ 拆成**证据层**与**出版层**两层。同时砍掉 `concept`（见 §2.0）。

```
dict            1,136,867   词级：身份 / 音标指针 / 语法本质 / 变形指针 / CEFR
├─ sense_src      390,774   源义项：某一版说的一句话，永不删改 ← 证据层
├─ sense          267,460   出版义项：用户读到的 1. 2. 3.     ← 出版层
│   ├─ sense_gloss  661,408   各语言的说法 ← 加语言只往这里加行
│   ├─ sense_tag    102,315   主题 / 地区 / 语域 / 数
│   └─ sense_relation ~200k    同义 / 反义 / 上下位（源头现成，一条没用）
├─ pronunciation      待建   读音（多变体、多记法、多地区）
├─ example         50,766   例句原文（西语）
│   └─ example_gloss  ✅建   例句译文（各语言）；`example.sense_id` 已挂 40,113 条
├─ collocation     28,960   搭配原文（西语）
│   └─ collocation_gloss ✅28,960 搭配译文
└─ audio           11,203   真人录音元数据
```

### 2.-1 两层义项：`sense_src`（证据）/ `sense`（出版）

**「义项」这个词在词典工程里指两件不同的东西**，v1 把它们混成了一张表：

| | `sense_src` 源义项 | `sense` 出版义项 |
|---|---|---|
| 是什么 | 某一版对这个词说的**一句话** | 词典里编号 **1. 2. 3.** 的那一条 |
| 谁写的 | 英文版编者 / 西语版编者 | 我们（编纂决策） |
| 可变吗 | **永不删改**（证据） | 可编辑、可重排 |
| 行数 | 390,774 | 267,460 |

```sql
sense_src(
  id, word_id,
  sense_id,      -- 编入哪条出版义项；NULL = 尚未裁决（默认不动比默认合并安全）
  src,           -- en-edition / es-edition …  ⭐记录的，不是从「有没有 en」反推的
  src_ref,       -- 回源坐标：dict:<id>#<行号> / sense_es:<id>
  lang, text,    -- 原文及其语言
  raw_tags       -- 原始标签原样留底，归一失败时能回查
)

sense(
  id, word_id,
  rank,          -- 展示顺序 1,2,3…（v1 那个混了两套来源的 idx 取消）
  pos, gender    -- 逐义项（el radio 半径 / la radio 收音机）
)
```

`ojo` 的样子：

    sense_src（29 行，永不动）              sense（25 行，用户读到的）
      #1 en "eye"              → sense_id=1   1. 眼睛
      #5 es "Órgano sensible…" → sense_id=1      对光敏感、使生物具有视觉的器官
      #2 en "keyhole"          → sense_id=2   2. 钥匙孔
      #11 es "Oquedad de las…" → sense_id=2      锁芯中插入钥匙的孔洞
      #8 es "Cualquier forma…" → sense_id=7   7. （用于几何）与眼睑开口相似的平面几何形

### 2.0 为什么砍掉 `concept`

v1 让 `concept` 同时干两件事，结果两头不靠：

| 职责 | v2 由谁干 |
|---|---|
| **词内合并**（`ojo` 的 en 义项与 es 义项是同一个意思） | `sense_src.sense_id` —— 更直接，且合并关系本来就是「归属」不是「等价」 |
| **跨词同义**（`ojo` 与 `globo ocular`） | `sense_relation` —— 那本来就是它的活 |

一张只有 `id` 的表两头不靠，砍掉。**可逆性一点没丢**：合错了改 `sense_src.sense_id`
一个整数字段就拆开，原文与译文一个字节不动，不用回滚备份、不用重跑翻译。

### 2.0.1 🔴 v2 最硬的一条理由：映射不能存成行号

**我们花 752 万 tokens 算出来的 80,521 条义项映射，现在存的是「`dict.definition` 的第几行」**
（`sense_es.en_i`）。这正是已经咬过三次的行号契约（`novia` 中英错位 / `esquela` 重编号
错位 / 指针混在释义列）。库里有四个脚本会改 `dict.definition` 的行
（`append_zh_senses` / `reorder_feminine_senses` / `fill_feminine_senses` / `fix_altof_lemma`），
**任何一次重排都会静默作废这批映射，且不会有任何报错**。

    现在   sense_es.en_i = 0        →  dict.definition 的第 0 行（字符串数组下标）
    v2     sense_src.sense_id = 42  →  sense.id（外键，重排也不会错）

⇒ 迁移的首要收益不是多语言，是**把最贵的那份产出从行号搬到主键上**。

### 2.1 目标语言内容与标签

```sql
sense_gloss(
  sense_id, lang, kind, seq, text, src,
  PRIMARY KEY(sense_id, lang, kind, seq)
)

sense_tag(sense_id, kind, value)   -- kind: topic / region / register / number
```

**`seq` 是 v2 加的**：一条义项的同一语言可以有**多个**对应词。
`ojo` 的中文是「眼睛；眼」，v1 只能塞进一个字符串用逗号分隔 ——
那是把「一列里塞数组」这个老毛病原样搬进新表。⇒ 两行，各带 `seq`。

`sense_tag` 用独立表而非 JSON 的理由是**可索引**：`escalera` 的"顺子"义带
`topic=poker`，要做主题筛选或按语域折叠粗俗义，JSON 字符串做不到。

⚠️ **标签取值必须跨版归一**：西语版写 `outdated`、kaikki 写 `dated`，
不归一按 `dated` 筛就漏掉 4,188 条。地区名保留原名（它们是实实在在不同的地方）。

`kind` 取 `equivalent`（对应词）或 `definition`（定义式），记的是**这条中文从哪种
原文翻来**：从英文对应词翻来 = equivalent，从西语单语定义翻来 = definition。

🔴 **但它不能拿来选标题行。** v1 定的规则是「对应词作标题、定义作副行」，
   2026-08-07 实测推翻：被判成 definition 的 17.2 万条里 **56% 本来就 ≤10 字**
   （`妓女` / `污水排水管` / `兰科植物属`），它们就是合格的标题。
   按 kind 选不但漏掉这批，还会误判出「需要再翻译 17 万条」这种**三倍于实际**的工作量。
   ⇒ 展示层取**最短的那条中文**当标题、明显更长的那条当副行，与 `kind` 无关，零成本。

⭐ **源语言的定义（es）和目标语言的翻译（zh/vi）在结构上是同一类行**，只是 `lang` 不同。
   英文 gloss 也不例外 —— 它本来就是「给英语用户看的翻译」。
   加一门语言 = 加一批行，**不改表结构、不加列**。

### 2.2 音标表

```sql
pronunciation(
  id, word_id, ipa,        -- 裸存，不带 /../ 或 [..]（沿用既有约定）
  notation,                -- phonemic | narrow
  region,                  -- es-ES / es-419 / es-AR / pt-BR / en-GB … ，null=通用
  tags, is_primary,
  src, src_confirm
)
```

同样是「把同一事物的多种正确变体从列变成行」。顺带解决四件积压的事：

1. pt 的 `ipa_br`/`ipa_pt`、en 的 `phonetic_uk`/`phonetic_us` → 统一成 `region`，**六语种结构真正同构**
2. `phoneticLatam` 不用再规则派生 —— 源头给了就用源头的，没给再派生并标 `src=rule`
3. `audio.ipa` 有了归属：每条录音本来就带自己的音标，可指向它实现的是哪条读音
4. 窄式记音（`s̺` 那类舌尖音附标）是 `notation=narrow` 的行 —— **存不存、展不展示成为两个独立开关**

#### 🔴 2026-08-19 补：读音归属要用**关联表**，单个可空外键装不下

`pronunciation.entry_id`（it 上后加的列）按「唯一才写」的规矩落值：一个读音属于
多个词条时只能写 NULL —— 而 `pesca` 的 `/ˈpɛska/` 在源头里同时挂在 `noun:1` 和
`adj:1` 下，`tramonti` 的 `traˈmonti` 名词（复数）与动词（第二人称）读音本就一样。
落 NULL 等于把区分力全丢：页面上两条读音并排堆在词头，用户不知道哪条配哪组义项。

```sql
pronunciation_entry(
  pronunciation_id, entry_id,      -- PRIMARY KEY (两列)
)
```

- 内容是旧列的**超集**：建表时先把 `pronunciation.entry_id` 非空的那批并进来，再加重算的（A95）
- 旧列 `pronunciation.entry_id` **不删**，作迁移锚点；**读取路径一律走关联表**
- 展示层判据是「**专属**」不是「属于」：一条读音若挂在该词形的每一个词条上，
  它就是共用读音 —— 词头那行已经显示过，不往组头铺
- it 实测：282,060 行关联，收回 **21,666 个词形**的归属，
  组头能标专属读音的词形 6,811 → **7,789**

⇒ 换语种时**直接建这张表**，别再走一遍「先单列、后发现装不下」。

#### 2026-08-19 补：`example.hidden`

与 `sense.hidden` 同一个约定。用于「源头确实收在该词条下、但对一部中文向词典没用」
的例句（it 上是 87 条古法语/拉丁/法语释义）。**藏不删** —— 判错了改回 0 就行。
🔴 加了列，读取路径（`exampleQuery`）必须同步加 `COALESCE(hidden,0)=0`，
否则就是「数据改了、页面照旧」那种最难发现的假绿。

## 五、迁移顺序

### 5.0 🔴 每一步必须过的三道闸（用户 2026-08-07 定）

> 「**不要把义项和释义错配了，那才是真灾难**」——`novia` 那一类错误的通用形式。
> 这类错**必须靠设计防住，不能靠事后抽样撞见**：抽 100 条看不出 0.3% 的错配，
> 而 0.3% 是 1,000 多个词条给用户看错的中文。

| 闸 | 做法 | 覆盖 |
|---|---|---|
| ① **可逆性回核** | 从新表**重建**出 `dict.definition`/`definition_es`/`translation` 的每一行，与库里**逐字节**比对，对不上一条就中止 | **100%，非抽样** |
| ② 不变量断言 | gloss 行数守恒 / 每条 sense 至少一条中文 / 无孤儿 / 主键无重复 | 100% |
| ③ 分层抽样人工核 | **只用于不能确定性验证的部分**——合并决策（哪些源义项编入同一条出版义项） | 抽样 |

⭐ ① 是关键：任何错配都会让重建结果与原文对不上。它把「义项和释义有没有配错」
   从一个抽样问题变成一个**可判定**问题。铁律「能确定性回源比对的根本别问模型」的
   直接应用。

1. ✅ **建 `sense_src` / `sense` / `sense_gloss` / `sense_tag` 四表**（2026-08-07，
   `es/pipeline/build_sense_layer.py`）。`dict` 14 项不变量全程零变化，`DROP TABLE` 即回到原状。

   | 表 | 行数 |
   |---|---|
   | `sense_src` 证据层 | **390,774**（en 147,240 / es 234,726 / 只有中文 8,808） |
   | `sense` 出版层 | **267,460** |

### 5.1 对齐质量核验结果

分层抽样 100 条（判为「新」50 + 判为「对上」50），逐条判：判对 **87** / 判错 **3** /
拿不准 **10**。准确率 87%（严格）～97%（宽松）。

但**决定安全性的不是准确率，是错误方向**：

| 错误类型 | 约占 | 后果 |
|---|---|---|
| 该匹配却判成「新」 | ~10% | ✅ 安全 —— 只多一条重复义项 |
| **匹配错了对象** | **2–4%** | ⚠️ 两个不同意思被并成一条 —— 改 `sense_src.sense_id` 一个整数就拆开 |

模型做对的那些相当有判断力，不是按下标瞎猜：
- `cuadro [5]`「操作设备的装置总成」→ 精确指 `[9] control panel`，**而非同下标的 `[5] table, chart`**
- `finta [0]`「税/贡赋」→ 指 `[1] tribute or tax`，**避开了最像的 `[0] feint`**

🔴 **两家顾问（豆包 pro + v4-pro）2026-08-07 一致否掉了「按对齐结果做父子义项」**：
> v4-pro：「不要用英文维基的义项树做父结构」——`ojo` 的 es#3「与眼睑开口相似的平面
> 几何形」能对齐到 eye，只是因为英文维基把「形状像眼的东西」也收进了那一条，
> **那是英语的词汇化方式，不是语义分类学**。它不是一种眼睛。
>
> 豆包 pro：「对齐结果是**语义相似度匹配**，不是词典学层面的**义位归并**」，
> 并指出照搬会把「孔眼」义族（针眼/网眼/桥孔…）拆散。

⇒ **没有 `parent_id`**。层级要做也该基于语义义族，那是编纂工作，对齐结果给不了。
   对齐结果只用来做「合并同一条义项」，不用来建树。

### 三个刻意的取舍

- **表名保留 `dict`**，不改成 `word`：176 个文件引用它，改名的收益只有语义整洁
- **变形关系（`infl`/`exchange`）这轮不动**：98 万行字符串，规范化成
  `form(word_id, base_id, tags)` 是对的，但它不挡多语言，留作第二阶段
- **每语种仍是独立的库、同一套 schema**：这是铁律「按语种解耦互不引用」。
  越南语用户查西语词典 = `synapse-dict-es.sqlite` 里多了 `lang='vi'` 的行，**不是新建库**

## 六、对查询的影响

**变慢的只有一处**：取完整词条从 1 次查询变成 5–6 次（word / sense / gloss / tag / example / audio），
都是主键或索引命中，SQLite 上微秒级，划词弹窗感知不到。

**变好的**（现在做不到或要靠字符串解析）：

| 查询 | 现在 | 之后 |
|---|---|---|
| 这条义项有哪些语言 | 做不到 | 一次索引查询 |
| 哪些义项缺越南语 | 做不到 | `NOT EXISTS(lang='vi')` |
| 按语域/主题筛义项 | 要解析 JSON | 索引命中 |
| 逐条义项的来源统计 | 只有词级近似 | 精确 |
| 某条义项的例句 | **做不到**（例句只挂在词上） | `example.sense_id` |

最后一条是顺带解锁的：`example.src_gloss`（记录该例句在源头挂在哪条义项下）
这座桥留了很久，**义项有稳定主键之后才用得上** —— "顺子"那条义项底下才可能显示扑克例句。

## 七、目标语言内容的三处出口

多语言化真正要动的只有三处 —— 它们形态完全一致：

| 原文表（语言无关） | 译文表（各语言） |
|---|---|
| `sense` | `sense_gloss(sense_id, lang, kind, text, src)` |
| `example` | `example_gloss(example_id, lang, text, src)` |
| `collocation` | `collocation_gloss(collocation_id, lang, text, src)` |

**加一门语言 = 往这三张表加行，别的地方一个字节不动。** 这是整套重构的验收标准。

### 7.1 `collocation` 是最脆弱的一列，不改就无法多语言化

28,960 条搭配现在把西语短语和中文**粘在同一个字符串里**，
展示层靠「从第一个汉字处切开」的正则分离：

    "entrada gratis 免费入场"  →  西语 "entrada gratis" + 中文 "免费入场"

现在 100% 切得开，但：

- 判据假设「中文里不含拉丁字母、西语里不含汉字」。一旦出现 `pH 值`、`X 光`
  这类，就从「分错一条」变成**静默错误** —— 切分发生在每次渲染时，不留痕迹
- 🔴 **越南语用拉丁字母，正则找不到「第一个汉字」，直接崩。**
  所以这一列不是「改了更好」，是**不改就做不了多语言**

拆开后顺带得到 `collocation.sense_id`：`pie` 的 `pie de página`（页脚）与
`pie de mesa`（桌脚）分属不同义项，现在都只挂在词上。

### 7.2 `example`：删 `dict_id`，加 `sense_id`

`example.dict_id` 是 **0 行非空**的半成品。填满它只是把「例句挂在词上」
再做一遍（`word` 列唯一且有索引，已经够了）。真正有价值的是 `sense_id`：

    escalera 的例句「Anna Politkóvskaia 在她公寓的**楼梯**上被击毙」
    明显属于义项 [0]（建筑构件），不是 [2]（扑克顺子）

挂载依据已经在库里：`example.src_gloss` 记录该例句在源头挂在哪条义项下，
**覆盖率 100.0%**（50,747 / 50,766）。⚠️ 但它是**源头那一版的语言**
（`escalera` 那条来自法语版，`src_gloss` 是 "Échelle, escalier."），
所以挂回义项需要跨语言判断，和义项合并是同一类工作，可以顺带做。

净效果：列数不变，查询路径不变，但例句从「挂在词上」升级成「挂在义项上」。

### 7.3 新语言：翻完再上，不做灰度

一门语言要么全部翻完、要么不出现在语言列表里。**不存在「部分翻译」的展示状态**，
因此不需要降级链（`vi → en → es`）这类运行时逻辑 —— 少一层。

判据就是一句查询，放在 `availableLanguages()` 现在判「DB 文件是否存在」的同一个位置：

```sql
SELECT COUNT(*) FROM sense s
WHERE NOT EXISTS (SELECT 1 FROM sense_gloss g
                  WHERE g.sense_id = s.id AND g.lang = 'vi');
-- 返回 0 才把越南语放进语言列表
```

> 曾经考虑过「先上高频 3 万词灰度试水」，**结论是不做**。
> 灰度是软件发布用来控制风险的手段，这里没有对应的风险：翻译质量靠抽样核对验，
> 不靠放一部分用户去踩；灰度既不降低出错概率，又保证让用户看到半截词典。
> 成本上也不构成理由 —— 实测每门语言约 **4 小时**墙钟
> （2026-08-06 翻 es 的 103,569 条义项用时 16 分钟，163 万条是它的 15.7 倍），
> 挂一晚上能翻两三门。

## 八、一条边界：不是所有数据都该「先存起来再说」

表结构清晰之后，很自然会想「数据全存，只是选择性展示」。这**对一半**：

- ✅ **同样正确的多种变体**（多版本释义、多口音音标、多条录音）→ 存全，展示是另一层决策
- ❌ **正确性存疑的数据** → 不适用。框架第一条判据是「错比缺更伤权威」：
  没有背书、也无法复算的猜测值，摆在那里比留空更糟。
  方针③「例句只认 kaikki，Tatoeba/OPUS 排除」不是展示决策，是**不让它进来**。

⇒ 准确的说法：**正确性有保障的、存；正确性存疑的，要么补到确定、要么留空。**

### 9.1 频次列 `freq_zipf` / `freq_lemma_zipf`（2026-08-07 落库）

两家独立收敛到三条：按词标 CEFR 站不住（CEFR 是学习者能力量表，不是词汇属性；
西语官方 PCIC 只到 B2 且按义项列）／覆盖不到的词一律留空不外推／底层该存客观频次。

⇒ 加了 `es/pipeline/build_frequency_layer.py`，来源 wordfreq 3.1.1（Apache-2.0，

🔴 **wordfreq 的三个陷阱**（详见脚本 docstring，都实测过）：
① 多词的 zipf 是**拼**出来的 —— `mierda a vete la` 打乱语序后与原句同值 4.16
② **词缀会被静默剥掉再查** —— `a-` 拿到介词 `a` 的 7.36，比多词更阴，

③ 大小写折叠 —— `Chad`/`chad` 同值，`freq_src` 打 `/case` 标记

⭐ **反查 `level` 的结论比预期好**：等级与频次**单调对应**（A1 中位 4.92 → C2 中位 1.66），
不是乱标。真缺陷集中在两处：

### 10.1 病灶：一行 `dict` 塞了源头的多个 entry

kaikki 的一个 **entry = (词形, 词性, 词源号)**，`build.py` 把同一词形的多个 entry
**合并成一行 `dict`**：`pos` 拼成 `"n/v"`、`ipa` 只留第一个。意语实测（英文版切片）：

| | |
|---|---|
| entry 总数 / 词形数 | 622,957 / 588,731 |
| **有多个 entry 的词形** | **30,220 个（5.1%）**，合计 64,446 个 entry 压成 30,220 行 |
| `pos` 被拼成 `n/v` 这类串的行 | 22,849 |
| **同形异读（entry 间音标集合不相交）** | **1,944 个词形**（重音位置不同 1,380 / 元音开闭 460 / 音段 74 / 噪声 30） |

后果是**用户看到错的读音**，且无法通过多存几个音标解决：

```
pesca  (noun,etym1) ˈpɛska 桃子·桃色      ← 一个读音对应「一组」义项
       (noun,etym2) ˈpeska 捕鱼·渔船·抽奖
ancora (adv ,etym1) anˈkora 仍然/再/更多
       (noun,etym2) ˈankora 锚            ← 库里只有 anˈkora，「锚」配的是副词的重音
abbagliati (verb,etym1) abˈbaʎʎati 命令式+ti
           (adj/verb,etym2) abbaʎˈʎati 分词阳性复数   ← 变形形，没有义项行可挂
```

### 10.2 为什么不是"给 `pronunciation` 加 `sense_id`"

**一个读音对应的是一组义项，不是一条。** `ˈpɛska` 对应「桃子」「桃色」两条义项。
`pronunciation.sense_id` 只能一对一 ⇒ 要么给每条义项复制一行读音
（`UNIQUE(word_id,ipa,notation)` 得拆开，`region/tags/src` 重复存 N 份），
要么再加一张关联表。而**中间单位本来就存在，且是源头自己的单位** —— 那就是 entry。

变形形（`abbagliati`）更直接：它**没有义项行**，`sense_id` 根本挂不上去。

⚠️ 两家顾问在这一问上分歧，两边的前提都经回源核对被推翻，记录在案：
- v4-pro 反对 entry 层，理由是「`abbagliati` 两条变形可能同词性同词源」——
  **实测不成立**，它们分属 etym 1 与 etym 2。全量核：音标在 entry **内**是一致的，
  8.1% 的 entry 内多音标是**真变体**（`robot` roˈbo/ˈrɔbot、`te` te/ˈte 重读与否）
- 豆包支持 entry 层但警告「搜索会出现同词形重复结果」——
  **前提错了**：entry 夹在 `dict` 与 `sense` 之间，`dict` 仍是一词形一行，搜索路径不变

### 10.3 结构

```sql
entry(
  id, word_id,          -- → dict.id（词形不变，仍是搜索与身份单位）
  pos,                  -- 单一词性，不再是 "n/v" 这种串
  etym_no,              -- 词源号；源头没编号记 0
  seq,                  -- 同键内序号，正常 0（见下）
  aux, conj,            -- 词条级语法本质（源头 forms[] 的 tags:["auxiliary"]）
  src, src_ref,         -- en-edition / kk-en:<词>:<词性>:<词源号>:<seq>
  UNIQUE(src_ref)
)
sense.entry_id          -- 义项归哪个 entry；NULL = 无 dump 来源（如只有中文的 22 条）
pronunciation.entry_id  -- ✅ 已加（it 阶段 4，2026-08-17）：读音归哪个 entry。
                        --    **只在源头里这个读音唯一属于一个 entry 时才写**，
                        --    NULL = 该词形各词条共用（`gratis` 形容词/副词同读音）。
                        -- 🔴 查询必须写 `entry_id = ? OR entry_id IS NULL`（wildcard），
                        --    **不是**「取不到再回落」—— 回落写法会让「有专属次读音的词条」
                        --    看不到共用的主读音。it 的 A57。
inflection.entry_id     -- ✅ 语义已定死（it 阶段 8，2026-08-18）：**原形的那个 entry**，
                        --    即「这个变形形属于原形的哪一个词条」。
                        --    NULL = 定不了（原形同词性多词源 / 原形悬空），**不猜**。
```

🔴 **`inflection.entry_id` 为什么必须定成「原形的 entry」**（it 阶段 8，2026-08-18）：

这一列原来按**来源分裂成两套语义**，各自内部一致、库内不变量全绿、展示层不读它
⇒ 查库看不出任何异常：

| 来源 | 条数 | entry_id 指向 |
|---|---|---|
| en 版 | 509,651 | **变形形自己的** entry（kaikki-en 把 `form_of` 写在变形形的词条里）|
| en 版 | 122,234 | 原形的 entry（变形形自己没词条时的回落）|
| fr 版 | 602,336 | 原形的 entry（fr 版把变形表写在原形词条里）|

判据不是偏好，是**哪个读法带信息**：变形形自己的 entry 从 `word_id` 一查就有（冗余），
而「`porto` 是 `portare`（动词）的变位形、不是 `porto`（名词·港口）的」**推不出来**，
只有源头知道。⇒ 定成后者，`fixes/repoint_inflection_entry.py` 重指 499,966 条、
清空 24,514 条（确定性 97.75%，其余留 NULL），断言进回归闸 C8。

🔴 **主键必须是内容派生的稳定复合键，不能是行序**（v4-pro 提的，与 §2.0.1 同源）：
`src_ref = kk-en:<词形>:<词性>:<词源号>:<seq>`。dump 重下、重排都不会失效。

**`seq` 为什么存在**：wiktextract 会把同一个维基章节切成多条 JSON
（`banana` 果实/颜色分两条、`finale` 两组义项分两条）。实测 1,813 组重复键中
**1,811 组的音标与词源文本完全相同 ⇒ 合并成一个 entry**（这不是 A7 禁止的"义项判重合并"，
是把 wiktextract 的切分还原成维基的一个章节，且**合并前断言音标与词源文本相同**，
不同就不合并）。剩 **2 组音标不同**（`sorti` verb·2、`infrociare` verb·0），
用 `seq=1` 分开。

### 10.4 语法本质分两层（`aux` / `transitivity`）

源头是**逐义项**给及物性、**逐词条**给助动词，我们此前两个都只存了词级单值：

| 事实（全量扫英文版切片） | 数 |
|---|---|
| 动词义项 tags 带 `transitive` / `intransitive` | 12,652 / 5,395（合计 **18,047**，占动词真义项 31%）|
| 建库时映射进 `meta` 的键 | 只有 `pos` / `lex` / `g` / `reg` ⇒ **这 18,047 条一条没收** |
| 有 `forms[].tags:["auxiliary"]` 的动词词条 | 14,368 |
| **两种助动词并存**的动词 | 819，其中 **635 个源头直接给了用法条件**（`èssere[goal]` / `avére[transitive]`）|

⇒ `sense.transitivity` 直接从义项 tags 落；`entry.aux` 从 `forms[]` 落；
那 635 个双助动词动词，用「义项及物性 ↔ 词条条件标签」**确定性推导**，不调模型。

🔴 `dict.aux` / `dict.transitivity` 降级为**由下层聚合出的派生值**（`both` = 「下钻看义项」），
不能与 `entry`/`sense` 各存一份真值 —— 否则就是本项目栽过的「两个真值长期漂移」。

#### 10.4.1 实际落法（2026-08-13 完成，两处推翻上面的写法）

**推翻①：不建 `sense.transitivity` 列，落成 `sense_tag(kind='grammar')` 行。**
及物性是**多值**的 —— 实测有 `ditransitive+transitive`、`impersonal+intransitive`、
`intransitive+pronominal+transitive`。塞进单列就要发明一套编码，发明的编码既失真、
又会变成第二份真值。判据：**互斥单值的落列（`gender`），多值的落行。**
值一律用源头原词（`transitive` / `intransitive` / `ditransitive` / `ambitransitive` /
`reflexive` / `pronominal` / `impersonal` / `copulative`），不改写。

**推翻②：`18,047` 这个数不准，全量重数是 `20,038`**（只算 transitive/intransitive 是 18,266）。
落库 **18,007** 条，三个口径严丝合缝：

    dump 带语法标签的义项 20,038 = 变形指针 1,849 + 按词形去重吃掉 182 + 落库 18,007

`entry.aux` 14,260 个词条（avere 10,381 / essere 3,058 / **both 821**）。
双助动词那 821 个里，**1,622 条义项**由「义项及物性 ↔ 词条条件标签」确定性定到了单一助动词，
写进 `sense.aux`；定不下来的（源头两个助动词都没给条件标签，如 `sapere`）不写，停在 `both`。

🔴 `sense.aux` 是**覆盖值不是复制值** —— 单助动词词条的义项一律留 NULL，
读取时取 `sense.aux ?? entry.aux`。不复制 = 结构上不可能漂移（闸②有一条专门断言它）。

**`dict.aux` 的处置**：本轮**不改数据**，但**读取路径已切走** —— 词头的助动词改为
从 `entry` 层聚合（`ItalianDictService.rollupAux`），`dict.aux` 只在 entry 层没有值的
变形词形上兜底（35,183 个，如 `nato`→essere 来自 `nascere`）。
理由：`rallentare` 的旧值是 `avere`，而源头给的是 avére[及物]+èssere[不及物]，
不切读取路径就会**同一页词头写 avere、义项写 essere**。
彻底退休这一列要等阶段 2 建好变形层的 lemma 指针。

### 10.5 顺序：entry 归属是阶段 1 的副产品

阶段 1 本来就要建 `sense_src` 把每条义项锚回 dump 原文。
`build.py` 生成 `definition` 的规则是确定性的（遍历该词形的所有 entry → 每个 entry 的
senses → 取 `glosses[0]` 归一空白 → **按词形去重** → 按 dump 顺序追加），
**复刻这个循环，每一行义项落在哪个 entry 上就同时算出来了**，不需要额外的对齐工作。

⚠️ 那条去重规则有个副作用要记账：`accettano` 的两个 entry（`atˈtʃɛttano` / `atˈtʃettano`，
两个不同的动词）释义文字**完全相同**，去重后只剩一行 —— 第二个 entry 连同它的读音**整个不可见**。

## 十一、v3 回补到 es（2026-08-20）

`entry` / `inflection` / `pronunciation_entry` 三张表是 v2 定稿**之后**做意语时才加的，
所以 es 停在 v2 的第一版。2026-08-20 逐张评估该不该补。

### 11.1 结论：补两张，**不补 `pronunciation_entry`**

| 表 | es | 判据 |
|---|---|---|
| `entry` | ✅ 已建 **117,667** 行 | 见 11.2 —— 理由与 it **不同** |
| `inflection` | ✅ 已建 **1,091,106** 行 | 旧列结构上给不了 `base_id` / tags / 闸 |
| `pronunciation_entry` | ❌ 不建 | 全量回源实测符合条件的只有 **14 个**词形 |

**读音那条的量法**（这是本轮最该记住的一条）：dump 里每个 entry 自带 `sounds`，
「不同词条读音是否不同」本来就**可判定**，不该问模型（判官纪律⑩）。
141,507 个有音标的西语词形，逐词条比对读音集，完全不相交的 **14 个**
（`pie` 脚/派、`deal`、`Nike`、`geta`…）。作为对照：

* 我自己第一把粗尺子（只折叠近音化）给 **13,742**
* 咨询的两家分别估 **~200** 和 **~2,500**

三个数错了一到三个数量级。**西语正字法基本音位化，it 的 `pesca`
/ˈpɛska/ 桃子 vs /ˈpeska/ 捕鱼那种「同拼写·不同词条·不同读音」在西语里不成系统。**
14 个逐条处理即可，不值得为它建一张多对多。

### 11.2 🔴 `entry` 在 es 的理由与 it 不同

it 的 `entry` 买的是词性轴与词源轴。这两条在 es 都不成立：

* **词性轴** `sense.pos` 早就有。`App.tsx:1249` 的 `senseHasPos` 2026-08-12 就把
  `llama`（羊驼）的「及物」徽标修掉了。我一开始把这个当成建 `entry` 的头号理由写了出来，
  **是错的** —— 只查了 `dict.transitivity` 列没查读取路径，又一次「量源头不量落点」。
* **词源轴** 在西语几乎是空的：全 dump 807,155 行只有 10,041 条带 `etymology_number`，
  同 (词形,词性) 多词源仅 **1,017 组**，且绝大多数是后缀（`-a` / `-ado`）。

真正的理由只有一条：**证据层锚在行号上**。

```
es  sense_src.src_ref = 'dict:3#1:en'        ← dict.id + definition 文本列第几行
it  entry.src_ref     = 'kk-en:pie:noun:3:0' ← 词形+词性+词源号，内容派生
```

`build_sense_layer.py:509` 把 `sense_owner` 的 **4,501 条人工归属**键在这个 `src_ref` 上，
注释写着「重建后仍稳定的回源坐标」。它不稳定 —— 记账本里
「`split_case_homographs` 的 4,501 条归属被 `build_sense_layer` 重建抹掉」正是这一批。
这是 §1.2 那条「按行号对齐已经咬过三次」的**第五次**。

⇒ `build_entry_layer.py` 复刻 `build.py` 的义项循环，给 **147,042 条**义项
（en-edition 证据的 98.85%）挂上内容派生的锚。旧 `src_ref` 不删，冻结成迁移锚点。

### 11.3 两把尺子：「证明复刻忠实」与「决定挂哪个锚」必须分开

第一版拿顺序兼做挂锚判据，**被位置咬了两次**：

1. 按 `dict.id` 升序拼多行证据 → `Andorra` 那 204 个大小写拆分桶全红
   （dump 里专名在前，小写行 id 小，一排序就反了）
2. 改成按拼写分派 → `a`/`A` 这类**折叠残留**（证据还躺在小写行上、按合并顺序排）又红

`build.py` 在桶内**按文字去重** ⇒ 文字在桶内唯一 ⇒ 文字就是可用的键，与顺序无关。
最终：顺序只用于报告保真度（104,751 行整行逐字节相同），挂锚按文字。判据没放宽，
仍是逐字节相等，只是不再依赖「第几条」。**这正是 §2.0.1 那条规则的又一次应用。**

### 11.4 `inflection` 的三处 es 专属取舍

* **不分流 `alt_of`**。it 阶段 2b 把 `alt_of` 移回了词条层；es 不做，因为那会改变
  页面「变位形式」块里显示什么 —— 是内容改动。改成加一列 `kind`
  （form_of 714,083 / es-edition 375,186 / prose 1,325 / alt_of 512）把区别记下来，
  迁移本身保持逐字节可逆。要不要分流，等看得见页面之后单独一轮再定。
* **不建 `base_entry_id`**。it 用它按名词词条筛复数，挡掉 `bello` 的性数一致形。
  es 实测这个病不存在：`dict.plural` 21,634 条里只有 296 条没有名词义项，
  逐条看是 `liberal → liberales` 这类**形容词复数**，西语形容词本来就有复数，是对的。
* **`baseForms` 继续读 `exchange`，不读 `inflection.base`**。这两列不是同一份东西：
  `build.py:305-330` 对 `exchange` 里的原形做过**人工裁决**。实测换过去 15,499 个词形会变 ——
  `absconder` 丢掉指向 `esconder` 的链接、`te` 冒出一个点不开的 `tú and vos`。
  **裁决过的那份才是真值；变形层给的是结构，不是原形裁决。**
